# 冒烟与截图自测：夹具、断言与阈值

## 现象

1. **13 条断言连续多轮恒红**（2026-10-01，176 条里）：失败项**逐字相同**、失败详情里出现"按设计"的拒绝文案
   （如 `该路径在项目根之外`）。根因是 v17/v18 把项目根从「全局 `projects.current`」改成**按会话解析**
   （未绑定会话恒落 Agent 空间 `桌面\Aurora`，而它**排在全局当前项目之前**），而 smoke 夹具仍只设全局 current、
   写目标又在 `userData` / `%TEMP%` 下 —— 这 13 条测的全成了「越界拒绝」。
2. **每轮白扔 2 分钟**：`await confirmTool(...)` 在夹具落不到 auto 档"根内"分支时会静默走进「等用户回执」
   （一个 60s 超时），而失败详情只显示 `approve:false noCard:true`，看着像"没批准"。
   （2026-10-05 起 `auto` 已改成完全权限直接返回，不再依赖"根内"夹具；这条保留作历史排查线索。）
3. **半条断言从没跑过却一直报 ok**：`!text.includes('skipped.txt')` 这类判据在调用本身失败时恒真
   （错误文案里当然没有那个文件名）；2.6 段只读档的"内容一字未变"同款（文件压根没被写成功过）。
4. **累计型阈值最先翻**：`droppedFrames`、`longTask.count`、`heartbeatOverrunMs` 这类「累计个数」在
   有背景负载时最先超限（本机是虚拟显示适配器压低合成器帧率），而单次最坏值
   （`maxLongTask` / `maxFrameGapMs`）仍在限内。
5. **断言写死了会被"正常工作"改变的数值**：`agent.loop.maxRounds === 8`（默认值已改 32）、
   "桩 LLM 收到 N 轮请求"这类计数，在无关改动后假失败。
6. **探针改配置有两个相反的缓存时机**：`SettingsStore.init()` 启动即把 `config.json` 读进内存并长期缓存
   —— 启动后**写文件对运行中的进程无效**，改配置只能走 `settings:update` IPC；而 `SessionStore` 是按会话
   **惰性**读盘且首次读即缓存，种会话文件必须赶在窗口第一次 `chat:history` **之前**
   （`runCapture` 里、`captureWindows` 之前）。
7. **夹具没覆盖"字段缺一半"的分支**：轨迹自动折叠原先只收「**思考增量**到达时被打开过的」消息，
   而桩 LLM 的默认分流**每轮都发 `reasoning_content`** —— "有工具调用、**没有**思考增量"那一轮一次都没被覆盖，
   bug 就活在 34 条全绿的探针底下；给桩加一条专用分流（`SKILL_ONLY_MARKER`）才造出现场。
8. **桩分流判断"第几轮"看错了范围**：判据不能看**整段历史**里有没有 `role: 'tool'`（长会话里前面的提问有），
   要看**最后一条 user 消息之后**有没有工具结果（`hasToolResultSinceLastUser`）—— 否则第 1 轮就回正文，
   探针报出"没有轨迹"这种看着像渲染坏了的**假 FAIL**。

## 原因

- 夹具是"按当时的口径"写死的：实现口径一变（项目根改为按会话解析、默认值调整），夹具不会自动跟着变，
  于是它测的不再是被测行为，而是"按新设计的拒绝路径"——以**恒红**的形式持续收税。
- 负对照型判据（"不该出现 X"）天然在"调用根本没成功"时成立，缺少"调用成功"这个前提就只能算半个断言。
- 累计型指标与机器负载强相关；写死数值的断言与"正常演进"冲突。

## 影响

- 恒红会训练人忽略红：真实的回归混在里面没人看；排查时还会把它误判成自己引入的。
- 静默超时（60s×N）让一轮冒烟从 25 秒膨胀到 2~3.5 分钟，直接吃掉排查预算。

## 结论与做法

- **判据**：连续多轮失败项**逐字相同**（不是抖动）+ 详情里出现"按设计"的拒绝文案 → 先怀疑**夹具过期**，
  再怀疑实现。修法是让夹具跟上新口径（如 `bindSmokeProject` 把夹具**绑定到会话**），
  别去"修"边界判定。
- **看见 `await confirmTool(...)` 先检查夹具**是否真能落到预期的授权分支；
  同段里"**故意**要弹卡"的那半（根外）走轮询 + `rejectAll`、**不等超时**，两者别混为一谈。
- 加判据时先问一句「**调用失败时这条会不会也成立**」——会成立就必须先断言调用成功。
- **累计型阈值第一次红不要改实现**：先隔离重跑该场景（回绿即环境噪声）；真要调阈值，
  按「夹具规模变了必须重新标定」连夹具一起调。
- 断言别写死会被"正常工作"改变的数值：改成 `>=`、或用与改动前实测值比较。
- 夹具要覆盖**"字段缺一半"的分支**：给桩 LLM 加专用分流造现场（`SKILL_ONLY_MARKER` 就是为
  "有工具调用、没有思考增量"那一轮加的），别假设默认分流已经覆盖了你要测的形态。
- 桩判断"第几轮"看**最后一条 user 消息之后**有没有工具结果（`hasToolResultSinceLastUser`），
  不是看整段历史。
- 端到端基线口径：冒烟全量一轮约 25 秒、183 条断言应全绿（`SUMMARY 183/183 passed`）；
  `AURORA_SMOKE_ONLY` **只切主进程侧那十几个段**（2.1~5），渲染层脚本（约 135 条断言）始终全跑，
  所以一轮下限仍在 20 秒上下 —— 它的价值是**聚焦**，不是把 24 秒压到几秒；**提交前必须跑全量**。
  跨进程续跑段用 `AURORA_SMOKE_PHASE='resume'` + `AURORA_SMOKE_WORKSPACE=<同一目录>`。
- 基线不是绿的，说明断言或夹具过期了：**先把基线修绿再动被测代码**，别在红基线上判断"这次是不是我引入的"。
- capture / smoke 夹具改配置**只能走 `settings:update` IPC**；种会话文件必须赶在第一次 `chat:history` 之前。
