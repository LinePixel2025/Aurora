# 吸底跟随：intentWindowMs、原生监听归属、合成事件测不到滚轮

## 现象

1. **滚轮逐次被吞**（2026-10-01 用户报「答完滚动不了历史」）：从底部往上滚，视口被"吸"回底部，
   回到底部的胶囊不出现。
2. **只有反向复核才看得见**：把修复 stash 掉后，探针实测 `{"distanceAfter":0,"capsule":false}`
   （滚动被抹掉、胶囊不出现）。
3. **换容器后滚轮 / 滚条 / 翻页键 / `scroll` 一起失效**：`rebind()`（自愈入口）只重挂了两个观察者，
   四条**原生监听**只在 `core.start()` 那一次被消费 —— 注释写了"每次 rebind 都重新挂一遍"，实现漏了。
4. **JS 合成事件测不出这一类问题**：用 `dispatchEvent(new WheelEvent(...))` 的探针在这条链上必然 PASS。

## 原因

- 跟随状态的判定最初挂在 `scroll` 事件上，于是"跟丢"；为修"跟丢"把判定挪到"真实输入"事件上后，
  又碰上输入事件与合成器滚动之间的时序：**输入事件到达主线程时，合成器可能还没把视口挪过去**
  （`passive: true` 的 wheel 尤其如此），那一刻读数仍是"贴在底部" → 判成"用户还在底部继续滚" →
  浏览器随后派发的 `scroll` 排出一帧对齐，把这一滚原样抹回底部。
- `dispatchEvent` 能驱动意图链路（监听器照收、判定照跑），但**不触发合成器滚动**；
  "程序把用户刚滚出去的视口吸回去"这类失效（意图与对齐帧的竞速、吸底补齐的时机）全都发生在
  合成器与主线程之间，合成事件面前必然 PASS。

## 影响

- 「跟丢」与「滚不动」是**同一条链的两个反向失效**：修好一个很容易把另一个弄坏，
  不能把前一版的语义当成"已经验过、不需要再验"。
- 没有能复现的探针，用户下次报同类问题时只能再猜一轮；而"前一版探针全绿"恰恰是最有欺骗性的前提。

## 结论与做法

- 判定**只由真实输入发起，但要看之后的读数**：真实输入开一个短窗口（250ms，
  `packages/shared/src/browser/composables/stickToBottomCore.ts` 的 `intentWindowMs`）按当前读数重判。
- 要测真实滚轮，走 `webContents.debugger` 发 CDP `Input.dispatchMouseEvent`（type `mouseWheel`），
  见 capture 的 `chat-trace-wheel` 探针与 docs/07 §5.2；**别用 `new WheelEvent` 下结论**。
- 探针的"前置"要如实复刻真实路径：旧探针（`CHAT_AUTO_SCROLL_SCRIPT` 与 `CHAT_FOLLOW_BURST_SCRIPT`）
  都是先把 `scrollTop` 拨到 0 再发滚轮，于是永远测不到
  "从底部往上滚"这条真实路径；新探针 `CHAT_FOLLOW_WHEEL_UP_SCRIPT` 复刻两拍
  （贴底 → 真实 wheel → 挪视口 + `scroll`）。
- **改原生监听时检查 `rebind()`**：注释里的承诺要当成待验证的断言读，别信它已经发生。
- 修复后做**反向复核**（把修复 stash 掉，确认探针会 FAIL），否则你无法区分"修好了"和"探针本来就不测这个"。
