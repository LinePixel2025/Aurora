# 顶部流光批量分析状态连续性

## 现象

文件自感知连续分析多个文件时，顶部极光会在每个文件结束的瞬间淡出，再随下一份文件开始
淡入，表现为反复闪烁。单文件分析正常。

## 原因

`FileAwarenessService` 在第一份文件收尾时先清空 `current` / `analysisStage` 并广播
`idle`，再延时 50ms 启动下一份。渲染层按 `analysisProgress.stage` 决定 `active`，
因此会把这次文件间交接解释成分析结束，触发约 180ms 的淡出；下一份开始后又反向淡入。
主进程的 220ms 原生隐藏去抖虽然阻止窗口真正隐藏，但无法阻止渲染层透明度来回切换。

## 影响

批量分析是常态，用户会持续看到极光反复出现 / 消失；若只把隐藏延时加大，下一次等待更久
的队列交接仍会复现。

## 结论与做法

- 文件自感知 `processQueue` 收尾时，只要队列仍有下一项且 provider / 授权 / 额度门控允许，
  就**先同步启动下一项，再决定是否广播空闲态**；只有批次真正结束或停在门控时才发 `idle`。
- 不要把 `queued` 直接等同于可显示：首次排队尚未开始时仍应隐藏流光；连续性应来自
  “下一项已经开始”的状态，而不是放宽显示条件。
- `WindowManager.showAwarenessGlow()` 在窗口已可见且工作区未变时保持幂等，不重复
  `setBounds` / `showInactive` / 置顶重置，避免状态更新额外扰动原生合成面。
- 回归护栏在 `apps/desktop/src/main/file-awareness.test.ts` 的批量文件阶段序列用例：
  第一份与第二份实际处理之间不得出现 `idle` / `queued`。
