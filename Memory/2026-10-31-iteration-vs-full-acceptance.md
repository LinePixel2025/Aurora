# 迭代期只跑定向验收，全量验收等用户说「提交」再跑

## 现象

一个只改 Computer Use 浮层 / 提示词的任务，净改动约 300 行，实际耗了约 25 分钟才提交。
其中改代码约 4 分钟，其余是「每轮任务结束都自动跑全量验收」：
typecheck + lint + 全量单测（2979 条）+ build + 271 条冒烟 + 117 条截图三轮，
再加两次自找的返工（`ELECTRON_RUN_AS_NODE` 处理错、截图窗口过滤漏了两个内部窗口）。

## 原因

`AGENTS.md` 原来的跑法预算写的是「迭代期只跑定向、全量放最后验收」，
但对「最后验收」没有触发条件，编码代理就默认在**每次任务收尾**都跑一遍全量。
全量成本 ≈ 12 分钟（冒烟 1.5 + 单测 2.5 + 截图 6 + build / 检查 2），
对一两百行的改动来说性价比很低；而且迭代中途跑全量，失败还可能是 flaky（Center 的两个并行用例）。

## 影响

- 小改动被验收成本淹没，用户感知是「改这么点东西怎么花了半小时」。
- 全量跑得越多，越容易被 flaky / 范围外恒红项干扰，反而拖慢真正要交付的改动。

## 结论与做法

**用户 2026-10-31 明确约定的口径**：

- **迭代期**：只跑「相关单测子集（`pnpm vitest run <相关文件>`）+ 定向截图（`AURORA_CAPTURE_ONLY` / 相关窗口）
  + 必要的 typecheck**；不跑全量单测、不跑冒烟、不跑全量截图。
- **用户说「提交」时**：再跑全量验收 —— typecheck / lint / 全量 test / build / 冒烟 271 / 截图 117 条三轮，
  绿了才提交并推送；红了先修，不提交（范围外恒红项 `chat-model-picker.png` 与环境 flaky 单独说明）。
- 用户没喊「提交」时，改动可以停在「定向全绿 + 工作区已落盘」的状态，不要自作主张提交。
- 一次性验收兜底：`Memory/2026-10-31-computer-use.md` 里的两条坑（`ELECTRON_RUN_AS_NODE` 要
  `Remove-Item` 而不是赋空串；`AURORA_CAPTURE_WINDOWS` 必须显式带上 `computer-use-overlay` /
  `computer-use-hud`）已在 `AGENTS.md` 的验收命令里修正，别再重复踩。
