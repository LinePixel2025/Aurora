# 记忆召回改相关性优先

## 现象

2026-10-25 用户定口径：**`memory-read` 不再强制读完全部记忆**，不管记忆库多大，只读与当前任务有关的条目。
改动前 `memory-read` 的硬口径是「索引 + 全部 `.md` 全量加载」（当时 79 条 / 333 KB / 4958 行，
其中约 2/3 与当次任务无关）。

旧版本自己写下了反对理由：「读之前做相关性筛选是不可靠的」—— 这条反对依然成立，
所以换口径时必须同时换上**让筛选可复核的机制**，而不是简单把"全部"删掉。

## 原因

- 全量加载的成本随库线性增长，而命中率随任务收窄而下降：一次改 CSS 的任务，读 20 条发布记录的边际价值接近 0。
- 相关性筛选本身不可靠的原因是**筛选方式**（凭感觉挑），不是"筛选"这件事：
  用从任务里提取的检索词 + 命中计分 + 放宽条件，筛选就从"感觉"变成"可复述的判断"。
- 漏读的代价不对称：漏一条"跨子系统的坑"要付一次返工，多读两条只是几百 token。

## 影响

- 删掉全量读之后，如果把**护栏**也一起简化掉，召回会静默退化：跨子系统改动（发布 / 配置 Schema /
  IPC 契约 / 权限 / 数据删除）只读到表面相关的两条，然后在错误的假设上干活，而且没有任何信号提示漏了。
- 反向风险同样存在：索引主题列写得含糊（"某某功能的问题"），相关性召回时根本不会被命中 ——
  索引质量直接决定召回率，`memory-summary` 优化索引不是美观问题。

## 结论与做法

1. **索引永远是必读的全量面**：`Memory/README.md` 一行一条，成本与库大小无关；没有索引就用文件名当索引。
2. **检索词从任务里来，不从感觉来**：路径 / 包、技术面、动作面（发布 / 改 Schema / 调样式）、现场串
   （报错原文、通道名、配置键）四类，写下来再选条目。
3. **计分选读**：检索词命中标签 / 主题 / 文件名 ≥ 2 条必读，命中 1 的截断到前 5–8 条。
4. **放宽条件必须保留**：跨子系统改动（发布、配置 Schema 与迁移、IPC 契约、权限、数据删除、主题令牌）
   把相关标签**整组读全**；用户点名主题时该组全读。
5. **二轮补读 + 兜底**：进入子系统前 grep `Memory/`；顺着「详见 Memory/xxx.md」读；
   读到被推翻的旧口径要找同组更新的那条；零命中时读最近 3 条并全文 grep 一次，
   不要用"索引里没写"直接下"以前没踩过"的结论。
6. **汇报必须说清跳过了什么**（`加载 6 条 / 跳过 73 条，最相关未读：xxx`）—— 这是唯一能让用户
   发现"漏读"的机制，不许把跳过说成读完。
7. **例外**：`memory-summary` 全库体检必须全量读（要判断"还有没有用"就得知道全库有什么），
   用户明确要求"都读一遍"时也照办。`AGENTS.md` 已同步这条口径。
